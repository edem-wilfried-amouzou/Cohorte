Architecture

Application

Django regroupe les comptes dans apps/accounts et les classes, personnes, activités, groupes et documents dans apps/groupes. Les pages sont rendues par les templates Django; les scripts navigateur sont dans static/js.

Données et fichiers

Le développement utilise SQLite par défaut. Si DATABASE_URL existe, Django utilise la base décrite par cette URL, généralement PostgreSQL en production. Les documents téléversés sont stockés sous MEDIA_ROOT, qui vaut media/ par défaut.

Construire et déployer

  1. Installer les dépendances Python avec pip install -r requirements.txt.
  2. Installer Tailwind avec npm ci, puis compiler les styles avec npm run build:css. La source se trouve dans static/src/tailwind.css; le résultat est static/css/tailwind.css.
  3. Contrôler la configuration avec python manage.py check --deploy, puis vérifier les migrations avec python manage.py makemigrations --check --dry-run.
  4. Appliquer python manage.py migrate, créer la table du cache avec python manage.py createcachetable, puis collecter les fichiers statiques avec python manage.py collectstatic --noinput.
  5. L’application WSGI se lance avec Gunicorn sur config.wsgi:application. La sonde /sante/ vérifie que l’application et la base répondent.

Le blueprint Render exécute la compilation CSS et collectstatic pendant la construction, puis les migrations et la création du cache au démarrage.

Variables d’environnement

VariableRôle
DJANGO_SECRET_KEYClé de signature. Obligatoire quand DJANGO_DEBUG=0; ne jamais la publier.
DJANGO_DEBUGActive le mode développement. Garder la valeur à 0 en production.
DATABASE_URLURL de connexion à PostgreSQL ou à une autre base prise en charge par Django.
DJANGO_ALLOWED_HOSTS et DJANGO_CSRF_TRUSTED_ORIGINSHôtes et origines autorisés si l’application utilise un domaine personnalisé.
DJANGO_ADMIN_URLChemin de l’admin Django. La console Cohorte reste disponible sous /console/.
MEDIA_ROOTRépertoire des documents. En production, le monter sur un disque persistant ou configurer un stockage objet.
SENTRY_DSNActive la remontée d’erreurs vers Sentry, sans collecte de données personnelles par défaut.

Contrôles de sécurité

  • Les vues de la console superadmin et les journaux d’administration vérifient le compte actif et le rôle superutilisateur.
  • Les formulaires utilisent la protection CSRF de Django. Les rôles de classe contrôlent les opérations de lecture et de modification.
  • Les liens partagés utilisent des jetons aléatoires. Les liens d’inscription et de consultation sont distincts et peuvent être renouvelés séparément.
  • Les téléversements sont limités à 25 Mo par fichier et 250 Mo par classe; une archive ZIP est limitée à 100 Mo.
  • En production, HTTPS, les cookies sécurisés, HSTS et les en-têtes de sécurité sont configurés par les paramètres Django.
  • Le service worker ne met pas en cache les pages privées ni les données de classe.

Les documents de production dépendent du stockage persistant configuré pour MEDIA_ROOT. Prévoir une sauvegarde distincte des fichiers et de la base.

Diagnostic rapide

  • État applicatif et base : ouvrir /sante/.
  • Configuration Django en production : lancer python manage.py check --deploy.
  • État des migrations : lancer python manage.py showmigrations.
  • Historique des actions sensibles et modifications de l’admin : consulter l’onglet Journaux.
  • Après un changement de styles ou templates, reconstruire Tailwind, puis exécuter collectstatic.
